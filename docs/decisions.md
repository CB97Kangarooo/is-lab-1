# Архитектурные решения

Журнал архитектурных решений по лабораторной работе (вариант 683). Каждая запись — решение + причина, используется как черновик отчёта и шпаргалка к защите.
---

## Шаг 0 — базовые решения

**Представление:** JAX-RS + React.
JSF сознательно не берём — уже был опыт, хочется освоить REST-подход, ближе к стеку, с которым дальше работать (Spring на стажировке).

**Сервер приложений:** WildFly 21.0.0.Final.
Определено по факту через SSH-доступ к серверу `helios` (`~/Servers/wildfly-21.0.0.Final`). Jakarta EE 8, namespace **`javax.*`** — это версия WildFly до перехода на `jakarta.*`. Все зависимости и импорты только `javax.*` (пример: `javax:javaee-api:8.0.1`, не `jakarta.platform:jakarta.jakartaee-api`).

**Coordinates:** `@Embeddable`.
Поля `x`/`y` не переиспользуются между героями и не выбираются из списка существующих объектов (в отличие от Car) — отдельная таблица была бы лишним JOIN без смысловой пользы. Поля хранятся прямо в колонках таблицы `human_being`.

**Car:** `@OneToOne`, FK `car_id` на стороне `human_being`, `nullable = true`, `unique = true`.
- Отдельное меню создания машин
- Машина может существовать без владельца.
- При удалении героя — каскадное удаление `Car`, безопасно, потому что уникальный constraint гарантирует, что владелец на этот момент максимум один (не заденет чужие данные).
- Список машин в UI при выборе — только свободные.

## Инфраструктура — WildFly и JDK

**Проблема:** системная Java на сервере helios — 17-я версия, несовместима
с WildFly 21 (риск `InaccessibleObjectException` в CDI/Hibernate при рефлексии
через модульную систему Java 9+).

**Решение:** установлен portable Eclipse Temurin JDK 11 без root-прав
в `~/jdks/jdk-11.0.32.1+1`. В `standalone.conf` перед проверкой `JAVA_HOME`
добавлена строка, явно указывающая на эту JDK. Подтверждено логом старта —
WildFly поднимается под 11-й Java.

## Шаг 2 — схема БД и сущности

**Схема пишется руками (`sql/schema.sql`), Hibernate в режиме `validate`.**
Hibernate только сверяет маппинг с реальной таблицей (наличие колонок и их типы), но не создаёт схему. Так все ограничения задания гарантированно живут в БД, а не зависят от того, что Hibernate решил сгенерировать.

**`id`: `BIGSERIAL` + `GenerationType.IDENTITY`, в Java — `Long`.**
Значение выдаёт sequence в БД (требование «генерировать средствами БД»). `Long`, а не `long`: `null` = «ещё не сохранён». `CHECK (id > 0)` — требование `id > 0` явно на уровне БД.

**`creationDate`: `@PrePersist` в Java, в БД — `NOT NULL` без `DEFAULT`.**
Hibernate вставляет *все* колонки, включая `creation_date = NULL`, поэтому `DEFAULT` в БД не сработал бы без `insertable = false` + `@Generated` и лишнего SELECT после вставки. С `@PrePersist` дата известна объекту сразу после `persist()`. `updatable = false` — дату нельзя переписать при обновлении. Один источник значения, `NOT NULL` в БД — страховка.

**Enum'ы: `VARCHAR + CHECK`, `@Enumerated(EnumType.STRING)`.**
`ORDINAL` хранил бы номер константы — перестановка констант в Java молча испортила бы данные. PostgreSQL `ENUM` потребовал бы кастомный тип в Hibernate 5.3.

**Имя: `CHECK (btrim(name) <> '')`, а не `name <> ''`.**
`@NotBlank` отклоняет строку из пробелов; `CHECK` сделан таким же строгим, чтобы уровни не расходились.

**Car: `cascade = REMOVE`, без `orphanRemoval`; FK `ON DELETE CASCADE`.**
- Герой → машина: удаляет JPA (`cascade = REMOVE`). БД так не умеет — FK лежит у героя, а `ON DELETE CASCADE` работает только от того, на кого ссылаются, к тому, кто ссылается.
- Машина → герой: удаляет БД (`ON DELETE CASCADE`), по требованию «связанные объекты удаляются».
- `orphanRemoval` не ставим: иначе `setCar(null)` удалял бы машину, а она должна оставаться свободной.
- `fetch = LAZY`: машина подгружается только при обращении; в REST отдаём DTO, собранные внутри транзакции.

**`validation-mode = CALLBACK`.**
При `AUTO` без провайдера Bean Validation проверка молча отключилась бы; `CALLBACK` в такой ситуации роняет деплой.

## Шаг 3 — репозиторий (Criteria API)

**Репозиторий: `@ApplicationScoped` CDI-бин без состояния, без собственных транзакций.**
Один экземпляр на приложение; `@PersistenceContext` даёт потокобезопасный прокси на persistence context текущей транзакции. Транзакцию открывает сервис, поэтому `findPage` и `countAll` выполняются в одной транзакции, а сущности остаются managed, пока сервис собирает DTO.

**Общий `buildPredicates(cb, root, car, filters)` для `findPage` и `countAll`.**
`Root` принадлежит одному запросу, а запросов два, поэтому условия строятся функцией от `root`, а не передаются готовыми. Логика фильтров в одном месте: условия `WHERE` в странице и в счётчике не могут разойтись.

**Фильтры — `Map<String, String>`, имена колонок проверяются реестром `HumanBeingColumns` (белый список).**
Имена от клиента нельзя подставлять в запрос напрямую (параметры защищают значения, но не имена). Один реестр обслуживает и фильтр, и сортировку; неизвестное имя — `UnknownColumnException`, а не 500 от Hibernate. Фильтровать можно по `name`, `car.name`, `mood`, `weaponType`; сортировать — по любой колонке.

**Фильтр: `lower(column) like lower('%…%') escape '\'`, enum приводится к тексту через `as(String.class)`.**
`%` и `_` в пользовательском тексте экранируются, иначе они работали бы как шаблонные символы. `lower` применяется и к колонке, и к шаблону, поэтому результат согласован при любой локали БД. `hibernate.criteria.literal_handling_mode=BIND` гарантирует, что строки уходят параметрами `?`.

**Репозиторий возвращает сущности; `Page<T>` и DTO собирает сервис.**
Репозиторий не знает про DTO и REST. Страница и общее количество собираются в сервисе в одной транзакции.

**`findPage`: fetch join для `car`; `countAll`: обычный join.**
`car` — `LAZY`, без fetch join сборка DTO дала бы N+1 запросов. В count-запросе fetch join недопустим.

**Отдельный count-запрос, offset/limit, `ORDER BY …, id` (tiebreaker).**
Для «страница N из M» нужно общее число записей. Без вторичной сортировки по уникальному `id` порядок при совпадающих значениях не гарантирован, и строки могут пропадать или дублироваться между страницами. `limit` ограничен 100 (`Pagination.MAX_LIMIT`), нарушение границ — `BadRequestException`.

**Статическая метамодель (`hibernate-jpamodelgen`).**
`root.get(HumanBeing_.name)` проверяется компилятором, опечатки и переименования полей находятся при сборке. Обращения к полям метамодели — только внутри лямбд реестра, потому что Hibernate заполняет их при старте приложения.

## Шаг 4 — сервисный слой

**Границы транзакций: `@Transactional(REQUIRED)` стоит на каждом публичном методе сервиса.**
Сервис объединяет несколько операций репозитория, проверку правил и сборку DTO в одну JTA-транзакцию; репозитории её не открывают. Аннотация не ставится на класс, чтобы транзакционность каждого публичного метода была видна явно. `EntityTransaction` не используем: транзакцией управляет контейнер WildFly.

**Публичные методы сервиса не вызываются через `this`.**
CDI применяет `@Transactional` через прокси; вызов `this.method()` обходит прокси и перехватчик, поэтому новая транзакционная семантика такого метода не сработает.

**Наружу передаются DTO, не JPA-сущности; координаты в ответе — вложенный `CoordinatesDto`.**
Так API не зависит от схемы БД и JPA-прокси, а `LAZY`-связь не окажется разыменована после закрытия транзакции. Вложенный DTO сохраняет структуру value object `Coordinates`; для машины во входных DTO передаётся только `carId`, чтобы клиент не мог неявно создать или изменить машину вместе с героем.

**Mapper'ы — CDI-бины только для структурного преобразования и не обращаются к БД.**
Поиск машины, проверка её доступности и остальные бизнес-правила остаются в сервисе. Сборка DTO выполняется внутри сервисной транзакции, поэтому доступ к `LAZY car` безопасен.

**Свободность машины проверяется сервисом, а `UNIQUE(car_id)` остаётся последней защитой от гонки.**
Перед привязкой сервис проверяет, что машина существует и свободна. Между этой проверкой и commit другой запрос всё ещё может занять машину, поэтому уникальное ограничение БД обязательно. Пессимистические блокировки не берём: для этого сценария они добавляют блокировки и риск ожиданий, а ограничение БД надёжно сохраняет инвариант.

**Изменения публикуются как CDI `Event<DataChangedEvent>`, наблюдатель работает в `AFTER_SUCCESS`.**
Сервис не зависит от WebSocket: на шаге 7 наблюдатель можно дополнить рассылкой. `AFTER_SUCCESS` гарантирует, что уведомление уйдёт только после успешного commit, а не во время транзакции, когда другой клиент мог бы ещё увидеть старые данные.

**Нет ручного `em.flush()` для валидации или перевода технических ошибок.**
Бизнес-условия проверяются до записи и дают доменные исключения; ошибки Hibernate и БД не перехватываются, их HTTP-представление появится на шаге 6. После `persist()` с `IDENTITY` Hibernate сразу выполняет вставку для получения id; `@PrePersist` уже установил `creationDate`, а Hibernate инициализирует `@Version`, поэтому принудительный flush для create не нужен.

**`HumanBeing.version` — `@Version Long`, колонка схемы — `BIGINT NOT NULL`.**
Версия защищает от потерянных обновлений: Hibernate включает её в `UPDATE ... WHERE version = ?` и увеличивает при успешном обновлении. Для уже существующей БД нужна миграция `ALTER TABLE human_being ADD COLUMN version BIGINT NOT NULL DEFAULT 0;`. Сервис заранее сравнивает версию из запроса с текущей и бросает `OptimisticLockException`; простое присваивание версии managed-сущности не заменяет проверку, потому что проверку конкурентности выполняет Hibernate при update/flush.

**`CarRepository.isFree` и фильтр `freeOnly` в `findPage`/`count` используют Criteria API с коррелированным `NOT EXISTS`.**
Свободной считается машина, для которой не существует `HumanBeing` с этой машиной. Запросы не строятся конкатенацией строк, поэтому сохраняют типобезопасность Criteria API.

**REST на шаге 4 не добавляется.**
Сервисный контракт пока вызывается только из будущего слоя представления; JAX-RS-ресурсы, `ExceptionMapper` и отладочные endpoint'ы появятся не здесь.

## Шаг 5 — специальные операции в БД

**Пять специальных операций реализованы как PL/pgSQL-функции в `sql/functions.sql`.**
Они исполняются на стороне PostgreSQL: агрегаты и выборка не требуют лишней передачи данных в приложение, а массовые изменения вместе с созданием машин выполняются атомарно в текущей транзакции. В PostgreSQL `FUNCTION` возвращает значение и вызывается через `SELECT`; `PROCEDURE` вызывается через `CALL` и не подходит такому контракту.

**Пустая сумма — ноль, пустое среднее — `NULL`.**
`sum_impact_speed()` использует `COALESCE`: сумма пустого набора естественно равна 0. `avg_impact_speed()` возвращает `NULL`: среднее пустого набора не определено, а 0 неотличим от настоящего среднего. `SpecialOperationService.averageImpactSpeed()` возвращает `Double`, REST отдаёт `null`. На уже развёрнутой БД функции обновляются повторным применением `sql/functions.sql` (`CREATE OR REPLACE`).

**`assign_lada_kalina()` создаёт одну новую `Lada Kalina` на каждого героя без машины.**
Связь `HumanBeing`—`Car` является `@OneToOne`, поэтому одна машина не может быть назначена нескольким героям. В исходной модели `Car` нет поля цвета; значение «красная» хранить негде, поэтому функция создаёт машину с именем `Lada Kalina` и `cool = true`, не выдумывая несуществующую колонку.

**Массовые функции вызываются через `EntityManager.createNativeQuery` из `SpecialOperationService`.**
Перед вызовом выполняется `flush()`, после — `clear()`: прямой `UPDATE` в БД не обновляет кэш первого уровня Hibernate. При фактическом изменении сервис публикует общее событие `HumanBeing UPDATED`, которое существующий наблюдатель получит только после успешного commit.

**Массовые функции сами увеличивают `version`.**
`set_all_mood_sorrow()` и `assign_lada_kalina()` меняют строки напрямую SQL-ом, минуя Hibernate, поэтому `@Version` сама не сработает: обе пишут `version = version + 1`. Иначе возможно потерянное обновление: клиент открыл героя с `version = 3`, массовая операция сменила `mood` (версия всё ещё 3), клиент сохраняет старую форму — `HumanBeingService.update` сравнивает `3 == 3`, проверка проходит, массовое изменение молча перетёрто. С увеличением версии такой `PUT` получает 409, как и при обычном конкурентном редактировании. Версию поднимает БД, а не приложение: `UPDATE` выполняется на стороне БД, и только там известно, какие строки затронуты.

**`assign_lada_kalina()` блокирует выбранные строки (`FOR UPDATE`).**
Без блокировки два одновременных вызова видели бы одного и того же героя без машины, оба вставили бы машину, второй перезаписал бы `car_id` — и машина первого осталась бы без владельца (сирота, которую `UNIQUE(car_id)` не отлавливает, потому что ограничение не нарушено). С `FOR UPDATE` параллельный вызов ждёт на заблокированной строке, после commit перечитывает её и пропускает: в READ COMMITTED PostgreSQL перепроверяет условие `WHERE` на новой версии строки. Здесь выбрана блокировка, а не ограничение БД, как в шаге 4 для `UNIQUE(car_id)`, и причина в природе операции: занять машину — действие одного клиента, его можно отклонить с 409, а массовая пересадка должна пройти целиком, и отклонять её нечем.

**Поиск по префиксу: функция БД отдаёт id, сущности загружает репозиторий.**
`find_by_name_prefix()` возвращает `SETOF human_being`, то есть колонок машины в выборке нет. Если отобразить результат прямо в `HumanBeing`, `HumanBeingMapper.toDto` обращался бы к LAZY-связи `car` по запросу на каждого героя (N+1) — ровно то, от чего в шаге 3 список защищён fetch join'ом. Поэтому нативный запрос берёт только `SELECT id FROM find_by_name_prefix(?)`, а `HumanBeingRepository.findAllByIds` загружает героев одним запросом с `LEFT JOIN FETCH car`: два запроса вместо `1 + N`. Требование «операция реализована функцией БД» соблюдено — отбор делает функция. Порядок задан одинаково в обоих местах (`ORDER BY id` в функции и в репозитории), поэтому результат не зависит от того, какой из запросов считать главным.

## Шаг 6a — REST-слой

**Список героев: `GET /api/human-beings?offset&limit&sort&order&filter.<колонка>`, ответ `{items, total, offset, limit}`.**
Параметры повторяют сигнатуру `HumanBeingService.getPage`. Имена колонок для `sort` и `filter.*` не проверяются в ресурсе: их проверяет реестр `HumanBeingColumns`, поэтому правило живёт в одном месте. Значения по умолчанию: `offset=0`, `limit=20`, `order=asc`, без `sort` порядок по `id`. К существующему `Page<T>` (`items`, `total`) REST-обёртка `PageResponse` добавляет `offset` и `limit`: клиенту не нужно хранить их отдельно от ответа. `Page` не менялся.

**Числовые и булевы query-параметры принимаются строкой и разбираются вручную.**
Если объявить `@QueryParam("limit") int`, RESTEasy на `limit=abc` отвечает 404 с английским текстом. Ручной разбор даёт 400 с русским сообщением через `BadRequestException`.

**Ошибки запроса — свой `BadRequestException`, а не `IllegalArgumentException`.**
Маппер на `IllegalArgumentException` ловил бы больше, чем нужно: от него наследуются `NumberFormatException` и исключение `Enum.valueOf`, поэтому любая внутренняя ошибка такого типа ушла бы клиенту как 400 с техническим английским текстом — и статус неверный, и внутренности наружу. `BadRequestException` (пакет `exception`, рядом с остальными доменными) бросают `QueryParams`, `RequestValidator`, границы offset/limit в репозитории и обязательный `prefix`; `UnknownColumnException` наследуется от него. Критерий простой: в тело ответа попадает только текст, который кто-то написал для пользователя. Непредвиденный `IllegalArgumentException` не перехватывается и доходит до `ThrowableMapper` — 500 с логом, как любая другая неожиданная ошибка. Перехват вокруг `SortOrder.valueOf` узкий — ровно один вызов в `try`.

**Валидация тела — явный вызов `Validator` (`RequestValidator`), а не `@Valid` на параметре ресурса.**
Для `@Valid` на параметре RESTEasy строит `ResteasyViolationException` без `ConstraintViolation` и с путями вида `метод.arg0.поле`. Явный `validator.validate(dto)` даёт пути относительно DTO (`name`, `coordinates.x`), поэтому ключи `fieldErrors` совпадают с именами полей запроса. Узлы метода и параметра в любом случае отбрасываются; для нарушений на уровне сущности `car` переименовывается в `carId`.

**Единый контракт ошибок: `{message, fieldErrors: {поле: сообщение}}` для всех кодов.**
`fieldErrors` присутствует всегда (пустой объект, если ошибка не про поле): клиенту не нужны проверки на `undefined`. Несколько нарушений одного поля склеиваются через `;`. Тексты сообщений на русском. Вся логика превращения исключения в ответ собрана в `ErrorResponses` и отделена от JAX-RS (`ApiError` — статус и тело); `ExceptionMapper`'ы делегируют туда; исключение — `WebApplicationExceptionMapper`, который сохраняет статус и заголовок `Allow` исходного ответа JAX-RS. Обёрнутые ошибки (`TransactionalException` → `RollbackException` → ...) разбираются по цепочке причин, поэтому ошибка, поднятая при commit, получает тот же код, что и поднятая в сервисе. Завёрнутый `WebApplicationException` сохраняет свой статус: проверка идёт последней в `fromKnown`, после доменных типов, которые точнее описывают причину. `WebApplicationExceptionMapper` собирает ответ с нуля, а не через `Response.fromResponse`: тот переносит все заголовки исходного ответа, включая `Content-Length`, не соответствующий новому телу; переносятся статус и `Allow` (он нужен клиенту при 405). `ThrowableMapper` не превращает `Error` (`OutOfMemoryError`, `NoClassDefFoundError`) в ответ: в таком состоянии приложение не готово собирать JSON, поэтому `Error` пишется в лог приложения и пробрасывается контейнеру — логирование до проброса сохраняет причину не только в логах WildFly.

**Коды статусов.**
- 400: нарушения Bean Validation; `BadRequestException` и его наследник `UnknownColumnException` (offset/limit, формат параметров); нечитаемый JSON и недопустимое значение enum (в сообщении перечислены допустимые значения `mood` и `weaponType`); пустое тело запроса.
- 404: `ResourceNotFoundException`; неизвестный путь; нечисловой или переполняющий `long` id (путь `/{id: [0-9]+}` не совпадает).
- 409: `CarNotAvailableException`; конфликт версий (`OptimisticLockException` из сервиса и `StaleStateException` при commit); нарушение `UNIQUE(car_id)` из-за гонки (в шаге 4 этот ограничитель назван последней защитой, здесь он получает HTTP-представление); нарушение внешнего ключа (SQLSTATE 23503).
- 405/415/406: статус JAX-RS сохраняется вместе с заголовками (`Allow`), тело приводится к общему формату.
- 500: всё неопознанное; в теле только общий текст, без stack trace, полная ошибка пишется в лог сервера.
- Успех: 201 + `Location` на создание, 200 на чтение и обновление, 204 на удаление.
Валидация даёт 400, а не 422: так задано требованием лабораторной, и у клиента один обработчик на все ошибки ввода.

**`carId`, которого нет в БД, при создании и обновлении героя даёт 404.**
Сервис бросает тот же `ResourceNotFoundException`, что и при чтении героя по id, а различать эти случаи в маппере пришлось бы по тексту сообщения. Клиент (UI) трактует 404 на POST/PUT как ошибку поля `carId`.

**JSON-B: `JsonbConfigProvider` (`ContextResolver<Jsonb>`) с `withNullValues(true)`.**
По умолчанию JSON-B пропускает `null`: `{"value": null}` превратился бы в `{}`, а `"car": null` исчез бы из ответа. RESTEasy берёт `Jsonb` из `ContextResolver`, если он зарегистрирован. Остальное — поведение JSON-B по умолчанию: enum строками, `LocalDate` в ISO-8601, вложенные `coordinates` и `car` объектами, поля в алфавитном порядке. Неизвестные поля запроса игнорируются; отсутствующие примитивы (`realHero`, `hasToothpick`, `coordinates.y`) принимают значения по умолчанию (`false`, `0`), потому что так объявлены входные DTO. `Jsonb` — `AutoCloseable`; провайдер `@ApplicationScoped` с `@PreDestroy`, закрывающим его при остановке приложения (если RESTEasy создаст провайдер сам, минуя CDI, `@PreDestroy` не вызовется — поведение остаётся прежним). `withNullValues(true)` работает, только если JSON отдаёт JSON-B: при Jackson-провайдере настройка не применится и `{"value": null}` схлопнется в `{}`. Проверка после деплоя: `curl` на `/api/special/impact-speed/average` при пустой таблице должен вернуть `{"value":null}`.

**Машины: `GET /api/cars[?offset&limit&free]`, `GET /api/cars/{id}`, `POST /api/cars`; в ответе у каждой машины `owner: {id, name}` или `null`.**
Один формат ресурса для чтения и создания: `CarWithOwnerDto` наследуется от `CarDto` и добавляет `owner`, JSON остаётся плоским (JSON-B сериализует унаследованные свойства наравне со своими; порядок — сначала свойства родителя). Наследование, а не копия трёх полей: новое поле машины появляется в обоих представлениях само, а маппер остаётся единственным местом, где поля машины перечислены. `POST /api/cars` возвращает тот же `CarWithOwnerDto` с `owner: null` (сослаться на только что созданную машину ещё некому; `withNullValues(true)` сохраняет поле), поэтому форма ответа совпадает с `GET /api/cars/{id}`.

Список — страница, как и список героев: `{items, total, offset, limit}`, один разбор ответа на оба списка, `total` показывает общее число машин даже при короткой странице. Выдача ограничена, потому что машин становится больше всего: `assign_lada_kalina()` создаёт по машине на каждого героя без машины. Предел и сообщение об ошибке живут в `Pagination` (`MAX_LIMIT = 100`), общем для обоих репозиториев; проверка стоит в слое репозитория, потому что защищает БД и действует при любом вызове сервиса, а не только из ресурса. Размер страницы по умолчанию (20) — `QueryParams.DEFAULT_LIMIT`, один для всех списков.

`CarRepository.findPage(offset, limit, freeOnly)` и `count(freeOnly)`: порядок по `id` (он же уникальный tiebreaker), `freeOnly` добавляет то же условие `NOT EXISTS`, которым определяется свободная машина, поэтому «все» и «свободные» не расходятся ни в порядке, ни в фильтре, а сортировки в Java нет. Владельцы собираются отдельным запросом `findOwners(Collection<Long>)` только для машин текущей страницы (без N+1; при `free=true` владельцы не запрашиваются вовсе), поэтому на список приходится два запроса при `free=true` (страница и счётчик) и три при `free=false` — независимо от размера страницы. У `Collectors.toMap`, собирающего `Map<carId, owner>`, есть функция слияния: дубликат `carId` невозможен из-за `UNIQUE(car_id)`, но ответ не должен падать 500, если схема нарушена. В `CarService` — `create`, `getPage`, `getById`. Эндпоинта удаления машины нет: в сервисе его нет. Если удаление появится, учесть: `ON DELETE CASCADE` в схеме удалит вместе с машиной её владельца.

**Спецоперации: `GET /api/special/impact-speed/sum`, `GET .../impact-speed/average`, `GET /api/special/human-beings?prefix=`, `POST /api/special/mood/sorrow`, `POST /api/special/cars/lada-kalina`.**
Чтение — GET, массовые изменения — POST. Массовые операции отвечают `{affected: n}` (число строк из функции БД). Параметр `prefix` обязателен (отсутствие — 400); пустая строка допустима и возвращает всех героев. Сумма: `{value: n}` (для пустой таблицы 0), среднее: `{value: x}` или `{value: null}`. Поиск по префиксу возвращает плоский массив без предела: задание требует «вернуть массив объектов», а страница или молча обрезанный результат изменили бы контракт операции; если объёмы вырастут, ограничение добавится вместе с остальными спецоперациями.

**`find_by_name_prefix` ищет префикс буквально.**
В `LIKE` символы `%` и `_` шаблонные, поэтому без экранирования префикс `%` вернул бы всех героев, а `_` — любое первое имя. Функция экранирует `\`, `%` и `_` и задаёт `ESCAPE '\'` явно (сначала `\`, затем `%` и `_` — иначе экранирующие слэши экранировались бы повторно). Это не вопрос безопасности (префикс передаётся параметром, функция только читает), а точность поиска. `starts_with(name, p_prefix)` (PostgreSQL 11+) дал бы то же поведение без тройного `replace`, но префиксный `LIKE` умеет использовать btree-индекс с `text_pattern_ops`, а `starts_with` — нет; выбран вариант, который не придётся переделывать при ускорении индексом. Регистр учитывается: `filter.name` в списке героев ищет без учёта регистра (удобство фильтра), а поиск по префиксу сравнивает буквально, как требует формулировка задания («значение поля `name` начинается с заданной подстроки»); расхождение осознанное. На уже развёрнутой БД нужно заново применить `sql/functions.sql`.
